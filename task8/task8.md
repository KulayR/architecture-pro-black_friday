# Мониторинг и устранение «Горячих» Шардов

## 1. Метрики мониторинга

Для своевременного обнаружения дисбаланса необходимо настроить сбор следующих метрик с каждого шарда (`shard1`, `shard2`...).

### А. Системные метрики
Позволяют увидеть физическую перегрузку узла.

| Метрика             | Описание                                   | Сигнал тревоги                                   |
|:--------------------|:-------------------------------------------|:-------------------------------------------------|
| **CPU Usage**       | Загрузка процессора на узле данных.        | Один шард > 80%, остальные < 20%.                |
| **Disk I/O (IOPS)** | Количество операций чтения/записи на диск. | Очереди на диск на одном шарде значительно выше. |
| **Network In/Out**  | Объём трафика.                             | Аномальный всплеск трафика на конкретном узле.   |

### Б. Метрики MongoDB
Позволяют понять природу нагрузки.

| Метрика                | Команда / Источник             | Описание                              | Сигнал тревоги                                         |
|:-----------------------|:-------------------------------|:--------------------------------------|:-------------------------------------------------------|
| **Queues (qr/qw)**     | `mongostat`                    | Очередь операций чтения/записи.       | Если `qw` или `qr` > 0 постоянно, шард не справляется. |
| **Lock %**             | `db.serverStatus().locks`      | Время ожидания блокировок.            | Высокий % блокировок на коллекцию `products`.          |
| **Operation Counts**   | `db.serverStatus().opcounters` | Кол-во query/update/insert в секунду. | Дисбаланс ops/sec между шардами более 30-40%.          |
| **Chunk Distribution** | `sh.status()`                  | Количество чанков на каждом шарде.    | Один шард хранит значительно больше чанков или данных. |
| **Jumbo Chunks**       | Логи балансировщика            | Наличие неперемещаемых чанков.        | Появление флага `jumbo` в метаданных чанка.            |

### Пример проверки нагрузки через консоль (mongostat)
Запуск утилиты для просмотра состояния всех узлов кластера:
```bash
# discover - показывает все узлы кластера
mongostat --discover --host mongos1:27017 
```
*Ищем строки, где Load/CPU/Ops зашкаливают относительно соседей.*

## 2. Механизмы устранения дисбаланса

В зависимости от корневой причины (неудачный ключ или временный всплеск), применяются разные стратегии.

### Стратегия А: Автоматическая балансировка (штатный режим)

Если ключ шардирования выбран удачно, но данные накопились неравномерно, должен сработать встроенный балансировщик.

1.  **Проверка состояния балансировщика:**
    ```javascript
    sh.getBalancerState() // Должно быть true
    sh.isBalancerRunning()
    ```
2.  **Настройка окна работы:** Чтобы перемещение данных не тормозило магазин днем, настройте окно на ночь:
    ```javascript
    use config
    db.settings.updateOne(
       { _id: "balancer" },
       { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
       { upsert: true }
    )
    ```

### Стратегия Б: Ручное разделение чанков

Если образовался **Jumbo Chunk** (слишком большой кусок данных, который нельзя переместить), его нужно разделить вручную. Это актуально для категории «Электроника», если она лежит одним куском.

```javascript
// 1. Находим большие чанки
use config
db.chunks.find({ jumbo: true })

// 2. Принудительно делим чанк (если ключ позволяет)
sh.splitFind("somedb.products", { category: "electronics" })
```
*Примечание: Если ключ шардирования - просто `category`, разделить чанк "electronics" невозможно, так как все документы имеют одинаковое значение ключа. Требуется Стратегия В.*

### Стратегия В: Уточнение ключа шардирования

Поскольку проблема в том, что все товары «Электроника» имеют одинаковый ключ `{ category: "electronics" }`, нам нужно добавить уникальности этому ключу, чтобы «размазать» категорию по разным шардам.

Можно использовать команду `refineCollectionShardKey` для добавления суффикса к существующему ключу без остановки базы.

**Решение:** Изменить ключ с `{ category: 1 }` на `{ category: 1, _id: 1 }`.

1.  **Создаем новый индекс:**
    ```javascript
    use somedb
    db.products.createIndex({ category: 1, _id: 1 })
    ```
2.  **Уточняем ключ шардирования:**
    ```javascript
    sh.refineCollectionShardKey("somedb.products", { category: 1, _id: 1 })
    ```
    *Что это даст:* Теперь MongoDB сможет делить огромный чанк «Электроника» на более мелкие поддиапазоны, основываясь на `_id`. Балансировщик сможет перенести часть электроники на другие шарды.

### Стратегия Г: Полная смена ключа

Если текущая схема не поддается лечению, можно выполнить живое перешардирование на более эффективный ключ, предложенный в задании 7 (`{ _id: "hashed" }`).

```javascript
sh.reshardCollection("somedb.products", { _id: "hashed" })
```
Это полностью устранит проблему "горячей категории", так как товары любой категории будут распределяться по хешу ID равномерно по всем узлам.

### Стратегия Д: Зональное шардирование (Zone Sharding)

**Решение для изоляции нагрузки или распределения мощностей.**
Если "Электроника" слишком популярна, мы можем выделить под неё группу мощных шардов (или, наоборот, принудительно размазать её по всем шардам, а редкие товары убрать на отдельный).

*   **Сценарий:** У нас есть 3 шарда. Шарды 1 и 2 — мощные (NVMe), Шард 3 — старый (HDD). Мы хотим, чтобы вся "Электроника" жила на 1 и 2.

*   **Реализация:**
  1.  **Тегирование шардов:**
      ```javascript
      sh.addShardTag("shard1RS", "hot_zone")
      sh.addShardTag("shard2RS", "hot_zone")
      sh.addShardTag("shard3RS", "cold_zone")
      ```
  2.  **Назначение диапазона ключей:**
      (Требует уточненного ключа из Стратегии В: `{ category: 1, _id: 1 }`)
      ```javascript
      // Направляем электронику в горячую зону
      sh.addTagRange(
        "somedb.products",
        { category: "electronics", _id: MinKey }, // От начала категории
        { category: "electronics", _id: MaxKey }, // До конца категории
        "hot_zone"
      )
    
      // Направляем остальные товары (например, книги) в холодную зону
      sh.addTagRange(
        "somedb.products",
        { category: "books", _id: MinKey },
        { category: "books", _id: MaxKey },
        "cold_zone"
      )
      ```
      *Результат:* Балансировщик переместит все чанки с электроникой только на `shard1` и `shard2` и будет распределять нагрузку между ними.

## 3. Кэширование как мера защиты

Даже при идеальном распределении данных, один шард может страдать от **Read Hotspot** (все читают одну и ту же запись популярного iPhone).

Для предотвращения этого необходимо:
1.  **Использовать Redis** для хранения карточек популярных товаров.
2.  Настроить TTL кэша для «Электроники» на разумное время (например, 1-5 минут).
3.  Запросы на чтение (`find`) должны сначала идти в Redis, и только при промахе - в MongoDB.

## 4. Резюме

Для устранения текущей проблемы с категорией «Электроника»:

1.  **Немедленно:** Проверить наличие `Jumbo Chunks`.
2.  **Краткосрочный фикс:** Применить `sh.refineCollectionShardKey("somedb.products", { category: 1, _id: 1 })`, чтобы позволить дробить монолитный блок электроники.
3.  **Долгосрочный фикс:** Мигрировать на `hashed` шардинг по `_id` (как спроектировано в задании 7), так как это гарантирует защиту от перекосов по категориям.
4.  **Мониторинг:** Настроить алерты на `qr/qw` и дисбаланс операций в `mongostat`.
