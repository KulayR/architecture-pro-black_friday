# Схема данных и стратегия шардирования

## 1. Коллекция `products` (Товары)

Эта коллекция характеризуется **высокой частотой обновлений** (изменение остатков при каждой покупке) и **сложными поисковыми запросами** (фильтрация по цене/категории).

### Схема документа (JSON)
```json
{
  "_id": "ObjectId('65a123...')",
  "name": "Смартфон X",
  "category": "electronics",
  "price": 59990,
  "attributes": {
    "color": "black",
    "storage": "256GB"
  },
  // Используем массив для удобства индексации по конкретным зонам
  "stock": [
    { "region": "msk", "quantity": 50 },
    { "region": "ekb", "quantity": 30 },
    { "region": "kld", "quantity": 15 }
  ],
  "updated_at": "ISODate('2025-12-31T12:00:00Z')"
}
```

### Стратегия шардирования
*   **Shard Key:** `{ _id: "hashed" }`
*   **Тип шардирования:** Хешированное.

### Обоснование
1.  **Равномерное распределение записи:** Самая частая операция записи - это обновление поля `stock` (списание товара). Эти операции идут по идентификатору товара (`_id`). Хеширование гарантирует, что "горячие" товары (например, новые iPhone) будут равномерно разбросаны по разным шардам, предотвращая перегрузку одного шарда при распродажах.
2.  **Избежание огромных частей:** Если выбрать `category`, то категория "Электроника" может стать слишком огромной и неделимой, что сделает балансировку невозможной.
3.  **Особенности чтения:** Поиск по категориям (`find({ category: "audio" })`) будет использовать опрос всех шардов. Для каталога товаров это допустимо, так как чтение часто кэшируется, а количество шардов обычно не исчисляется сотнями.

### Команды MongoDB
```javascript
use somedb
sh.enableSharding("somedb")
// Создаем хешированный индекс
db.products.createIndex({ _id: "hashed" })
// Включаем шардинг
sh.shardCollection("somedb.products", { _id: "hashed" })
```

## 2. Коллекция `orders` (Заказы)

Коллекция растет бесконечно. Критически важна скорость вставки нового заказа и скорость отображения истории заказов пользователю в личном кабинете.

### Схема документа (JSON)
```json
{
  "_id": "ObjectId('78b456...')",
  "user_id": "ObjectId('507f1f...')", // Идентификатор клиента
  "created_at": "ISODate('2025-12-31T10:00:00Z')",
  "status": "processing", // new, processing, shipped, delivered, cancelled
  "total_amount": 12500,
  "region": "msk",
  "items": [
    {
      "product_id": "ObjectId('65a123...')",
      "name": "Наушники Y",
      "price": 12500,
      "quantity": 1
    }
  ]
}
```

### Стратегия шардирования
*   **Shard Key:** `{ user_id: "hashed" }`
*   **Тип шардирования:** Хешированное.

### Обоснование
1.  **Локализация данных пользователя:** Это ключевой момент. Все заказы одного пользователя будут лежать на **одном** шарде.
    *   Операция `db.orders.find({ user_id: "..." })` (история заказов) будет направлена роутером (`mongos`) только на один конкретный шард.
2.  **Равномерность записи:** Пользователи создают заказы хаотично. Хеширование `user_id` равномерно распределит нагрузку по созданию заказов между всеми шардами.
3.  **Почему не `_id`?** Шардирование по `_id` размазало бы заказы одного пользователя по всем шардам, превращая сбор истории заказов в тяжелую операцию.
4.  **Почему не `region`?** Если шардировать по геозоне, то шард "Москва" будет перегружен, а шард "Калининград" будет простаивать.

### Команды MongoDB
```javascript
// Создаем индекс
db.orders.createIndex({ user_id: "hashed" })
// Включаем шардинг
sh.shardCollection("somedb.orders", { user_id: "hashed" })
```

## 3. Коллекция `carts` (Корзины)

Особенность коллекции: высокий оборот данных (создаются, обновляются и удаляются очень часто). Данные временные.

### Схема документа (JSON)
```json
{
  "_id": "ObjectId('99c789...')", // Уникальный ID корзины
  "user_id": "ObjectId('507f1f...')", // Может быть null для гостя
  "session_id": "xyz-123-session",    // Для гостей
  "status": "active", // active, ordered, abandoned
  "created_at": "ISODate('2025-12-31T08:00:00Z')",
  "updated_at": "ISODate('2025-12-31T08:05:00Z')",
  "expires_at": "ISODate('2026-01-01T08:05:00Z')", // TTL поле
  "items": [
    {
      "product_id": "ObjectId('65a123...')",
      "quantity": 2
    }
  ]
}
```

### Стратегия шардирования
*   **Shard Key:** `{ _id: "hashed" }`
*   **Тип шардирования:** Хешированное.

### Обоснование
1.  **Высокая скорость записи и удаления:** Корзины - это высоконагруженная на запись сущность. Хеширование по первичному ключу (`_id`) обеспечивает идеальное распределение записи.
2.  **TTL:** Удаление старых корзин фоновым процессом MongoDB будет распределено по всем шардам, не нагружая один конкретный сервер.
3.  **Специфика доступа:**
    *   При создании корзины мы получаем `_id`.
    *   При добавлении товара мы знаем `_id` корзины (обычно фронтенд хранит ID текущей корзины). Обновления по `_id` будут прямыми и быстрыми.
    *   *Минус:* Поиск корзины *только* по `session_id` или `user_id` (при первом заходе на сайт) будет тяжелым запросом (поиск по всем шардам). Однако, учитывая, что активных корзин обычно меньше, чем исторических заказов, и поиск идет по индексу, это допустимый компромисс ради равномерной записи и утилизации места.
    *   *Альтернатива:* Можно шардировать по `session_id`, но тогда сложнее гарантировать уникальность `_id` кластерно, и `user_id` все равно потребует тяжелых запросов.

### Команды MongoDB
```javascript
// Создаем хешированный индекс для шардинга
db.carts.createIndex({ _id: "hashed" })

// Создаем обычные индексы для поиска
db.carts.createIndex({ session_id: 1, status: 1 })
db.carts.createIndex({ user_id: 1, status: 1 })

// Создаем TTL индекс для автоудаления
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })

// Включаем шардинг
sh.shardCollection("somedb.carts", { _id: "hashed" })
```
