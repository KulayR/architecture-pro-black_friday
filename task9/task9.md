# Настройка консистентности и чтения с реплик

## 1. Сводная таблица стратегий чтения

| Коллекция    | Операция                                                           | Target (Узел)        | Допустимый лаг | Обоснование                                                                                                                                                       |
|:-------------|:-------------------------------------------------------------------|:---------------------|:---------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **products** | **Поиск товаров в каталоге** (фильтры, категории)                  | `secondaryPreferred` | 5–30 сек       | Высокая нагрузка на чтение. Если пользователь увидит товар, который закончился 5 секунд назад, это не критично на этапе поиска.                                   |
| **products** | **Просмотр карточки товара** (цена, описание)                      | `secondaryPreferred` | 5–15 сек       | Описания и цены меняются редко. Кэширование на уровне приложения или чтение с реплики оправдано.                                                                  |
| **products** | **Проверка остатков при добавлении в корзину / Чекаут**            | **`primary`**        | **0 сек**      | **Критично.** Риск продажи отсутствующего товара. Данные должны быть абсолютно актуальны.                                                                         |
| **orders**   | **Отображение страницы "Спасибо за покупку"** (сразу после оплаты) | **`primary`**        | **0 сек**      | Пользователь должен сразу видеть созданный заказ, иначе возникнет паника, что деньги списались, а заказ пропал.                                                   |
| **orders**   | **Просмотр истории заказов** (Личный кабинет)                      | `secondaryPreferred` | 1–60 сек       | Исторические данные статичны. Статусы текущих заказов обновляются не ежесекундно.                                                                                 |
| **orders**   | **Сбор аналитики** (отчеты по продажам)                            | `secondary`          | Минуты / Часы  | Аналитические запросы тяжелые и могут заблокировать Primary. Актуальность «секунда в секунду» не требуется.                                                       |
| **carts**    | **Отображение текущей корзины**                                    | **`primary`**        | **0 сек**      | Корзина меняется очень динамично. Пользователь добавляет товар и сразу переходит в корзину. Любая задержка приведет к "исчезновению" товаров и отказу от покупки. |
| **carts**    | **Поиск "брошенных" корзин** (фоновая задача)                      | `secondary`          | Минуты         | Фоновый процесс для рассылки e-mail. Высокая актуальность не нужна, важно не нагружать основной узел.                                                             |

## 2. Обоснование по коллекциям

### Коллекция `products` (Товары)
*   **Чтение с Secondary:** Основной трафик магазина - это просмотр каталога. Это "тяжелые" агрегации и фильтрации. Перенос их на реплики позволяет масштабировать чтение. Мы допускаем, что на странице поиска будет написано "В наличии", но при попытке купить пользователь получит ошибку (так как финальная проверка идет через Primary).
*   **Чтение с Primary:** Операция **списания остатков** (`findAndModify` или транзакция) и финальная проверка доступности обязаны идти через Primary. Иначе мы продадим 51-й смартфон при наличии 50, что приведет к репутационным рискам и возвратам средств.

### Коллекция `carts` (Корзины)
*   **Только Primary:** Корзина - это сессионное состояние. Пользовательский опыт здесь диктует правило: "Я нажал кнопку - я увидел результат". Репликация в MongoDB асинхронна; даже задержка в 100мс может привести к тому, что пользователь добавит товар, перейдет в корзину, попадет на отстающую реплику и увидит пустоту. Это "блокирующая" проблема для конверсии.
*   **Исключение:** Фоновые задачи (аналитика брошенных корзин, очистка устаревших) могут читать с реплик, так как они не взаимодействуют с пользователем в реальном времени.

### Коллекция `orders` (Заказы)
*   **Primary для подтверждения:** Сценарий "Create Order -> Redirect to Status Page" требует чтения с Primary. Иначе возможна ситуация: заказ создан на Primary, репликация еще не прошла, пользователь перенаправлен на страницу статуса, которая читает с Secondary -> 404 Order Not Found.
*   **Secondary для истории:** Список заказов за прошлый год не меняется. Статус текущего заказа ("В пути") обновляется складской системой. Если пользователь увидит смену статуса на 10 секунд позже, это никак не повлияет на бизнес.

## 3. Техническая реализация (Примеры)

В драйверах MongoDB (например, `motor` для Python) это настраивается через опции `read_preference`.

### Настройка глобально (в строке подключения)
Для большинства запросов по умолчанию можно оставить Primary, либо SecondaryPreferred, если приложение готово к лагам.
```python
# По умолчанию читаем с реплик, если они доступны
client = AsyncIOMotorClient(
    "mongodb://mongos1,mongos2/?readPreference=secondaryPreferred&maxStalenessSeconds=120"
)
```

### Переопределение на уровне операций (в коде)

**А. Критическая операция (Чекаут / Корзина) - Строго Primary:**
```python
# Явно указываем primary, даже если глобально стоит secondary
async def get_cart_for_checkout(cart_id):
    # .read_preference strictly Primary
    cart = await db.carts.with_options(read_preference=ReadPreference.PRIMARY).find_one({"_id": cart_id})
    return cart
```

**Б. Каталог товаров - Secondary (с контролем свежести):**
```python
# Допускаем чтение с реплики, но только если она отстает не более чем на 90 секунд
async def list_products():
    secondary_pref = ReadPreference.SECONDARY_PREFERRED
    # max_staleness защищает от чтения с "мертвых" или сильно отставших реплик
    return await db.products.with_options(
        read_preference=secondary_pref
    ).find().to_list(100)
```

## 4. Метрики мониторинга задержки

Для безопасного использования Secondary необходимо мониторить метрику **Replication Lag**.

*   **Команда:** `rs.printSecondaryReplicationInfo()`
*   **Критический порог:** Если лаг превышает 60 секунд, необходимо временно переключать все чтения на Primary (автоматически драйвером через `maxStalenessSeconds` или через Circuit Breaker в приложении), чтобы пользователи не видели слишком старые данные.
