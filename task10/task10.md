# Миграция на Apache Cassandra

## Задание 10.1. Анализ применимости и выбор сущностей

### Анализ сущностей:

1.  **Товары (Products):**
    *   *Вердикт:* **Оставить в MongoDB.**
    *   *Причина:* Каталог требует сложной фильтрации (по цене, характеристикам, фасетный поиск). Cassandra умеет искать только по первичному ключу.
2.  **Заказы (Orders) - Транзакционная часть:**
    *   *Вердикт:* **Спорно (Гибридный подход).**
    *   *Причина:* Создание заказа требует списания остатков и проведения оплаты. Cassandra не поддерживает мульти-документные транзакции. Сам факт *создания* лучше оставить в Mongo, но *хранение архива* и *обновление статусов* - перенести в Cassandra.
3.  **История заказов (Order History):**
    *   *Вердикт:* **Мигрировать в Cassandra.**
    *   *Причина:* Критически важная для пользователя функция ("Где мой заказ?"). Паттерн доступа простой: "Дай все заказы пользователя X". Данные пишутся один раз и редко меняются (только статус). Огромный объем данных, который легко партицировать по пользователям.
4.  **Корзины (Carts):**
    *   *Вердикт:* **Мигрировать в Cassandra.**
    *   *Причина:* Самая горячая точка на запись в "Чёрную пятницу". Огромный поток обновлений (добавить/удалить товар). Данные временные, потеря одной позиции неприятна, но не фатальна (в отличие от финансовой транзакции). Cassandra идеально работает с автоудалением и высокой скоростью записи.

### Итоговый выбор для миграции:
Мы переносим **Корзины** и **Историю заказов**, так как именно они создают основную паразитную нагрузку на БД при наплыве пользователей и отлично ложатся на модель данных Cassandra.

## Задание 10.2. Концептуальная модель данных

В Cassandra моделирование идет "от запроса" (Query-Driven Modeling). Мы денормализуем данные под конкретные сценарии чтения.

### Сущность 1: Корзины пользователей (`carts`)

**Паттерн доступа:**
1.  Получить все товары в корзине пользователя.
2.  Добавить товар в корзину.
3.  Удалить товар.

**Схема таблицы (CQL):**
```sql
CREATE TABLE carts_by_user (
    user_id uuid,
    product_id uuid,
    product_name text,
    price decimal,
    quantity int,
    added_at timestamp,
    PRIMARY KEY ((user_id), product_id)
) WITH default_time_to_live = 604800; -- TTL 7 дней
```

**Обоснование ключей:**
*   **Partition Key (`user_id`):** Обеспечивает то, что вся корзина конкретного пользователя лежит на одной ноде. Это гарантирует чтение корзины за один запрос к диску.
    *   *Равномерность:* Пользователи имеют случайные ID, что дает идеальное распределение.
*   **Clustering Key (`product_id`):** Позволяет уникально идентифицировать строку внутри партиции. Позволяет быстро удалять/обновлять конкретный товар, не перезаписывая всю корзину.
*   **Hot Partitions:** Риск минимален. В корзине редко бывает более 100 товаров. Партиция останется маленькой (Кбайты), что очень эффективно для Cassandra.

### Сущность 2: История заказов (`user_orders`)

**Паттерн доступа:**
1.  Показать пользователю список его заказов (от новых к старым).
2.  Найти конкретный заказ по ID (реже).

**Схема таблицы (CQL):**
```sql
CREATE TABLE orders_by_user (
    user_id uuid,
    order_id uuid,
    order_date timestamp,
    total_amount decimal,
    status text,
    items_json text, -- Денормализованный список товаров для превью
    PRIMARY KEY ((user_id), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC);
```

**Обоснование ключей:**
*   **Partition Key (`user_id`):** Все заказы пользователя хранятся вместе. При запросе "Мои заказы" Cassandra читает одну партицию последовательно.
*   **Clustering Key (`order_date` DESC, `order_id`):**
    *   Сортировка по дате (DESC) позволяет мгновенно отдавать последние N заказов (наиболее частый запрос) без сортировки в приложении.
    *   `order_id` добавлен для уникальности (если два заказа в одну миллисекунду).
*   **Влияние решардинга:** В Cassandra используется **Consistent Hashing** и **VNodes**. При добавлении новой ноды она забирает маленькие кусочки диапазонов хешей от других нод. Перемещение данных происходит фоново и *точечно*, не блокируя работу всего кластера, в отличие от Chunk Migration в Mongo.

## Задание 10.3. Стратегии обеспечения целостности

Cassandra - это "Eventual Consistency". Нам нужно выбрать инструменты для гарантии того, что данные не потеряются и сойдутся на всех репликах.

### 1. Hinted Handoff (Временное хранение записи)
*   **Как работает:** Если нода-реплика недоступна (перегружена или упала), координатор сохраняет запрос у себя ("подсказку") и отправляет его, когда нода вернется.
*   **Применение:** **Для всех сущностей (Carts, Orders).**
*   **Обоснование:** Это первая линия обороны для обеспечения высокой доступности записи. В "Чёрную пятницу" кратковременные тайм-ауты неизбежны. Hinted Handoff позволяет не возвращать ошибку пользователю, даже если часть кластера "штормит".

### 2. Read Repair (Восстановление при чтении)
*   **Как работает:** При чтении данных координатор опрашивает реплики. Если данные различаются (checksum mismatch), он возвращает клиенту свежую версию и *фоново* обновляет устаревшие реплики.
*   **Применение:**
    *   **Корзины (`carts`):** **Обязательно.** Пользователь часто обновляет страницу корзины. Механизм Read Repair будет "бесплатно" чинить расхождения данных при каждом обновлении страницы.
    *   **История заказов (`user_orders`):** **Желательно.** Клиент часто заходит проверить статус ("Отправлен ли заказ?"). Read Repair гарантирует, что статус синхронизируется на всех репликах.
*   **Chance:** Можно выставить `dcl_local_read_repair_chance = 0.1` (чинить 10% запросов), чтобы не нагружать систему в пик.

### 3. Anti-Entropy Repair
*   **Как работает:** Тяжелый фоновый процесс, который сравнивает все данные на репликах и синхронизирует их.
*   **Применение:**
    *   **История заказов (`user_orders`):** **Критично.** Это долгоживущие данные. Если Hinted Handoff был потерян (нода лежала долго), только Repair восстановит данные. Это нужно запускать по расписанию (раз в неделю/сутки), но *не в пик нагрузки*.
    *   **Корзины (`carts`):** **Не нужно.** У корзин есть TTL (например, 7 дней). Если данные рассинхронизировались и никто их не прочитал (Read Repair не сработал), они просто удалятся. Запускать тяжелый Repair для временных данных бессмысленно.

### Сводная таблица стратегий

| Сущность            | Consistency Level (Write/Read)  | Hinted Handoff | Read Repair | Anti-Entropy Repair | Обоснование                                                                                                                             |
|:--------------------|:--------------------------------|:---------------|:------------|:--------------------|:----------------------------------------------------------------------------------------------------------------------------------------|
| **Корзины**         | `LOCAL_QUORUM` / `LOCAL_QUORUM` | **Да**         | **Активно** | Нет                 | Данные временные, важна скорость. Read Repair починит расхождения "на лету".                                                            |
| **История заказов** | `LOCAL_QUORUM` / `LOCAL_ONE`    | **Да**         | Средне      | **Да**              | Данные постоянные. Repair нужен для гарантии сохранности архива. Read Level можно понизить до ONE для скорости, если Repair регулярный. |
